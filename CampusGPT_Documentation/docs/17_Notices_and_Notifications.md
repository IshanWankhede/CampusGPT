## 1. Purpose
Targeted notices from admin, dean, HOD and faculty with categories, priorities, attachments, rich text, scheduling, expiry, read tracking, acknowledgements, archive and search; in-app notifications for system events.

## 2. User roles
| Role | Capabilities |
|---|---|
| STUDENT | Read notices targeted to them; acknowledge; search; receive notifications |
| FACULTY | Publish notices to own classes; manage own notices |
| ADMIN | Publish institution/department notices; manage all; archive |

## 3. Functional behaviour
- Audience targeting by institution, department, branch, year, class, role.
- Scheduled publish and expiry; expired notices archive automatically.
- Read receipts and optional acknowledgements.
- Notifications are generated by events (new notice, assignment due, attendance shortage, role decision) and shown in-app.

## 4. Business rules
- Users only receive notices their audience rules match.
- Rich text is sanitised on the server before storage and again on render.

## 5. Frontend responsibilities
- Notice feed with filters and search; composer with audience picker; notification bell and list.

Cross-cutting UI rules (doc 33): dark mode only, Tailwind v4 tokens, Lucide React icons, loading/empty/error states, keyboard accessibility, reduced-motion respected.

## 6. Backend responsibilities
- `notices` and `notifications` modules; an internal event function creates notifications transactionally with the triggering action.

## 7. Database requirements (PROPOSED)
- notices(id, author_id, title, body_html, category, priority, publish_at, expires_at, requires_ack)
- notice_targets(id, notice_id, scope_type, scope_id)
- notice_reads(notice_id, user_id, read_at, acknowledged_at)
- notifications(id, user_id, kind, title, body, link, created_at, read_at)

All tables are created by additive Alembic migrations after reading the real revision head. Foreign keys to `users` reuse the existing table; no second user table is created. Institution scoping follows the outcome of PD-07.

## 8. API contracts (PROPOSED)
| Method | Path (PROPOSED) | Allowed | Purpose |
|---|---|---|---|
| POST | `/api/v1/notices` | FACULTY, ADMIN | create |
| GET | `/api/v1/notices` | any | visible notices (paged, searchable) |
| POST | `/api/v1/notices/{id}/read` | any | mark read |
| POST | `/api/v1/notices/{id}/ack` | STUDENT | acknowledge |
| GET | `/api/v1/notifications` | any | list own |
| POST | `/api/v1/notifications/{id}/read` | any | mark read |

Conventions: JSON, `/api/v1` prefix, Pydantic request/response models, pagination `?page=&page_size=` (default 20, max 100) on list endpoints.

## 9. Authentication
Existing JWT bearer authentication (after Stage 0: 15-minute access token with refresh rotation). All routes above require an authenticated, verified, active user unless stated otherwise.

## 10. Authorisation
- Faculty targets are restricted to classes they teach; designations (HOD/Dean) widen scope within their department/institution (PD-14).

Roles are read from the database on each request. Permission checks live in the service layer, not only in route decorators, so internal callers (such as AI tools) cannot bypass them.

## 11. Validation
- HTML sanitisation allow-list; attachments validated like uploads; publish_at < expires_at.

## 12. Error handling
All errors use the standard envelope from `10_API_Specification.md` (`{ "error": { "code", "message", "request_id", "details" } }`): 401 unauthenticated, 403 forbidden, 404 not found **or** hidden-by-permission (never reveal existence of unauthorised records), 409 conflict, 422 validation, 429 rate limited, 503 dependency unavailable.

## 13. Security
- Stored-XSS prevention; audience filtering done in SQL.

## 14. Testing
- Visibility matrix across roles/audiences; XSS payload neutralised; expiry/archive job; acknowledgement idempotency.

Plus: authorisation matrix tests (each role × each route), pagination bounds, and a regression run of the Foundation suite.

## 15. Dependencies

- File storage

## 16. Acceptance criteria
- No user sees a notice outside its audience.
- Sanitised rich text.

Acceptance additionally requires: tests actually executed and reported, migrations reviewed, docs and status files updated, and no claim of completion for UI-only work (see the six completion levels in `IMPLEMENTATION_STATUS.md`).
